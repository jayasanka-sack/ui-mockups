The platform

A clinical data platform and a modern EMR, in one project.

OpenMRS stores patient records in a structured, standards-based database and gives health workers a web application to use them: OpenMRS 3, or O3. You configure it for your clinic or country rather than writing a system from scratch, and you can extend it with your own apps, forms and modules without changing the core.

What's in the box

Four parts, one project.

Most people run the Reference Application and never think about the layers. Builders and integrators will want to know what sits where.

01 · WHAT YOU DEPLOY

Reference Application

The assembled, ready-to-run distribution: core, frontend, standard modules and starter content, shipped as Docker images and a standalone zip. Current version 3.8.0.

02 · WHAT USERS SEE

O3 frontend

A set of React microfrontend apps: registration, chart, forms, orders, queues, appointments, admin. Add your own app without touching the others. esm-core 11.0.0.

03 · WHAT HOLDS THE DATA

Platform core

The Java data model, services and APIs that every distribution shares: patients, encounters, observations, orders, concepts. MariaDB or MySQL underneath. Version 2.8.10, patched monthly.

04 · WHAT MAKES IT YOURS

Modules & content

Backend modules (FHIR2 4.3.0, REST 3.6.0, and hundreds more) plus content packages: forms, concepts, locations, report definitions. Your own can be public or private.

How you extend it

Change what you need. Keep the core.

Five layers of customisation, from a settings page to your own application. Start at the top; most deployments never reach the bottom.

  1. 01 · No code

    Configure

    Locations, identifiers, visit types, roles, languages, branding. Settings and JSON config, no build step.

  2. 02 · No code

    Build forms

    Design clinical forms in the Form Builder, with skip logic, calculations and validation. Publish without a deploy.

  3. 03 · Content

    Manage content

    Concepts from CIEL or your own dictionary via Open Concept Lab; programs, order sets, reports. Versioned and shareable.

  4. 04 · Java

    Write modules

    Add services, data types, integrations or scheduled jobs as a module that plugs into the core API.

  5. 05 · React

    Add frontend apps

    Ship your own microfrontend into the O3 shell: a new page, a widget on the chart, a whole workflow.

Why not fork the core? Because a fork stops receiving upgrades, security fixes and new apps the day you make it. Everything above is designed so you never have to. If the core is missing something you need, bring it upstream and every country gets it.
